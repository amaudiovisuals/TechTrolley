## Same trusted Wi-Fi route

Use one reviewed **separate real staging hostname**, a new trusted certificate/key
and a Mac LAN port such as24443 forwarded over the pinned private VM SSH connection
to guest127.0.0.1:443. The guest's SSH configuration already permits local TCP
forwarding; no host/public SSH daemon or router port-forward is needed. The active forward binds only192.168.29.240:24443. `staging.example.test` is only a placeholder,
not a domain for obtaining a publicly trusted certificate.

```text
Android Chrome / iPhone Safari (same reviewed origin)
  -> reviewed Mac LAN address:24443
  -> private SSH/virtual-socket forward
  -> guest HTTPS Nginx:443
  -> private Unix Gunicorn socket
  -> synthetic staging DB/media only
```

Both phones must resolve the reviewed hostname to that Mac's current LAN address
(local DNS or another reviewed DNS route). Use a stable reserved LAN address and
check the Wi-Fi has no client-isolation rule blocking phone-to-Mac access. DNS
resolution and certificate validation are separate checks. Phone localhost points
at the phone, not this Mac. The app also treats localhost/127.0.0.1 as development
and selects port8000, so use the reviewed hostname consistently for staging.

For a public domain controlled by the owner, DNS-01 certificate validation can
work without exposing the staging web server publicly. Use only the separate
staging name/challenge record, a new private key and the least DNS authority
needed; leave live routing unchanged. Choose a reviewed ACME client/account and
verify renewal/chain/expiry before enabling access. Issuance completed using manual DNS validation; future renewal still requires a reviewed manual or automated process.
[Let's Encrypt DNS-01](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge)

Camera access requires a secure browser context. Test with HTTPS trusted by both
phones, matching hostname and complete chain; do not use certificate-warning
bypasses, disable verification, enable browser insecure-origin flags or reuse a
production private key. A manually installed local CA would require a separate
device-trust procedure; it is not the default route in this plan.
[Browser camera requirements](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

An SSH TCP forward makes requests appear to the guest as loopback. Therefore
guest CIDR127.0.0.1 **does not restrict the original phones** and their peer login
budget is shared. Review the trusted LAN access boundary or an explicit Mac/router
restriction before opening it; do not accept spoofable client-IP headers to work
around this. Do not flush/replace existing firewall rules. This limited two-phone
synthetic test must not be presented as a production network design.
